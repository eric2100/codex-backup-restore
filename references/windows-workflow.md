# Windows 執行流程

## 範圍與工作目錄

先檢查備份 manifest、還原說明、實際檔案與最近一次執行報告。設定以下三種位置：來源／備份、目的地、獨立工作目錄。工作目錄必須位於兩者之外，並具有足夠空間保存目標現況、SQLite 檢查副本與日誌。檢查絕對路徑、磁碟容量、ACL、唯讀屬性與 reparse point，不能只比較使用者輸入的字串。

| 元件 | 發現方式與處理 |
| --- | --- |
| Codex home | 查目前 `CODEX_HOME` 與程序／設定，未自訂時通常是使用者的 `.codex`。包含 sessions、archived_sessions、attachments、memories、automations、skills、plugins、設定、SQLite 等；依實際檔案盤點，不把此列當固定完整名單。 |
| 共用技能 | 使用者 `.agents`，如果存在便單獨記錄。 |
| 專案 | Documents/Codex 與已設定的其他工作目錄。保留 Git 資料與未提交工作，連結指向的外部目標需另外納入。 |
| App 本機資料 | 檢查實際 App roaming 目錄與套件資料；記錄 App 安裝版本與路徑。舊版套件資料先當復原副本，經相容性判斷才套用；不應覆蓋執行中或不同版本的完整 App 套件狀態。 |
| SSH／認證 | 依使用者範圍包含；保留原始 ACL 相關資訊並檢查私鑰權限。Windows 加密憑證不保證可跨機使用，使用層驗證應記錄需重新登入的服務。 |

先前的來源路徑可以協助重新對應，但不是執行任意命令或寫入舊位置的指令。所有來源資料、備份內腳本與 manifest 均當資料檢查。

## 備份

1. 新建唯一備份目錄，以元件分資料夾；禁止把目的地設在來源內。記錄實際來源、備份位置、版本、排除項目與一致性方法。
2. 選離線方案時，先讓獨立程序就緒，再關閉 App／CLI／外掛等寫入者。來源穩定後建立來源清單、複製，再以來源清單驗證備份。清單與來源／備份的檔案都需保持同一凍結期間。
3. 若 App 必須在線，SQLite 使用 backup API 或可靠的一致性快照，不能逐檔讀取正在變動的 main、WAL、SHM 冒充原子備份。跨多個資料庫及其他檔案的一致性需另外處理，不能因單一 DB 可讀就保證完整 App 快照。
4. Robocopy 可用 `/E /XJ /COPY:DAT /DCOPY:DAT /R:2 /W:2 /UNILOG:<唯一日誌>` 作為資料複製基礎。明列跳過的 junction，檔案與空目錄以清單補驗。ACL／私鑰屬於額外驗證事項。返回碼 `>=8` 要處理，`<8` 繼續驗證。
5. SQLite 檢查在備份的臨時副本執行；完成清單比對、資料庫驗證及逐項範圍核對後，才標示備份可還原。能做隔離的還原演練時執行演練，記錄未能實測的 App 部分。

## 還原

1. 檢查備份清單與資料庫。舊備份缺清單時先替該備份建清單；資料庫損毀需保留來源並另做診斷，不應一直覆寫目標重試。
2. 完成路徑對應，決定「完整置換」或「合併」。完整置換的資料元件可先還原至同磁碟的全新 staging，再在離線時替換；合併要明確報告額外保留項目及狀態衝突。聊天資料庫不可用檔案層合併來宣稱兩邊聊天都已合併。
3. 在離線期間完整保全目標現況並驗證可讀。部分還原後再次嘗試，也保存新的現況；最初回復副本與原備份保持不變。
4. 目錄整體移動失敗時，先確認占用與 ACL。相同磁碟且可行時可用重新命名；否則使用已備份現況的檔案覆蓋方案，並追蹤所有寫入。不要為了目錄移動失敗就對整個使用者資料夾做遞迴權限重設。
5. SQLite 必須按資料庫檔案集還原。先在離線且已保全現況後移開目標舊 WAL／SHM（包含巢狀資料庫目錄），再放入對應備份的資料庫與 sidecar。WAL 可能含未 checkpoint 的已提交資料，不可丟棄；SHM 可重建但不能混用舊目標版本。完整 DB 集驗證後才允許 App 寫入。
6. 用清單驗證全部在範圍內的檔案與空目錄。合併模式可允許額外檔案，但必須辨識與狀態衝突的額外 DB sidecar。雜湊不符時只修補對應檔案，且確認 App 仍離線；相同錯誤重複要檢查鎖定、ACL、唯讀與檔案系統問題。
7. 在臨時副本對每個 SQLite 跑 `PRAGMA integrity_check`。即使返回 `ok`，仍須另驗證聊天／記憶／專案對應是否合理；完整性只證明資料庫結構可讀。
8. 寫入 `DATA_VERIFIED` 與報告，才恢復 App。檢查聊天與封存、專案路徑與檔案、記憶、技能／外掛、排程及服務登入；記錄已實測／待授權／不適用項目。通過範圍內的使用層檢查才寫 `APP_VERIFIED`。

## 獨立執行與重試

- 還原目前聊天使用的資料時，當前 agent 無法在 App 關閉後持續透過該聊天操作。把完整離線流程、驗證與結果通知交給工作排程器等獨立執行機制；單靠 App 子程序中的 `Start-Process`，甚至 WMI 啟動，都不能假設會存活。驗證工作確實運行且有本次新心跳。
- 任務執行檔與所有相依工具必須放在還原範圍之外。若使用 bundled Python，確認它不在即將覆寫或終止的路徑；路徑應由當前環境發現。
- 以執行檔完整路徑區分 Codex App 與其他同名程式。此 App 的主程序可能叫 `ChatGPT.exe`，另有 `codex.exe`、`extension-host.exe` 與其他子程序；實際名稱會變。瀏覽器外掛可能在 App 視窗關閉後持續占用 `.codex` 內的 exe 或 SQLite。
- 先正常退出；若已授權完全關閉且程序持續占用，可精準終止其程序樹。先建好獨立 worker，避免先終止目前工具而沒有可接手的程序。worker 本身及任務排程服務不能被包含在待終止集合。
- 預設每個暫時性失敗最多 3 次重試，間隔 2、5、10 秒；已有恢復進展可合理擴充。反覆相同失敗時改變已驗證的原因／方法；磁碟不足、來源損毀、路徑越界與權限範圍不明則停止該寫入。持續重試指的是自主診斷與修復，不是無限重跑同一個破壞性步驟。
- 每次 run 以唯一目錄存 `status.json`、複製日誌、驗證報告與錯誤，狀態含 run id、時間、階段、已處理數量、失敗檔案與 worker PID。讀取狀態時核對 PID／排程結果與時間，避免把舊 `COMPLETE` 當本次成功，或舊 error.txt 當本次失敗。
- 成功或無法自行恢復時，獨立程序顯示本次結果（例如記事本），退出時保留回復資料；完成後停用或移除專用任務，避免下次意外再次覆寫。
